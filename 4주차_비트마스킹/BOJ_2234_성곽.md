# BOJ 2234 — 성곽

- **날짜**: 2026-06-01
- **유형**: 플러드필(DFS) + 비트 벽 판정 + 확장 브루트포스
- **결과**: 자력 해결

## 핵심 테크닉
- 각 칸 값(0~15)은 벽을 비트로 인코딩: `bit 1=서, 2=북, 4=동, 8=남`. `(board & (1<<i)) == 0`이면 그 방향에 벽 없음 → 이동 가능.
- DFS 플러드필로 방을 칠하면서 **방마다 번호(`roomNum`) 부여** + **방 번호별 크기(`roomSize`) 캐싱**.
- 답 3개:
  1. 방 개수 = DFS 시작 횟수
  2. 가장 큰 방 = 영역 크기 최댓값
  3. 벽 하나 제거 시 최대 = 모든 칸×4방향 순회하며 **인접 칸이 다른 방 번호면 두 방 크기 합**으로 갱신

## 잘한 부분 / 떠올린 핵심
- "방에 번호를 붙이고 크기를 캐싱해 두면, ret3는 인접한 다른 번호 방끼리 크기를 더하기만 하면 된다"는 발상.
- 이게 처음에 안 떠올랐던 부분 — **브루트포스의 확장 버전**(단순 탐색을 넘어, 탐색 결과에 메타데이터=번호/크기를 입혀 2차 가공)을 체득.

## 막혔던 포인트
- 단순 플러드필로 방 개수/최대 크기까지는 갔으나, **세 번째 답(벽 제거 후 최대)**을 어떻게 O(저렴)하게 풀지가 막혔음.
- 해결: 방 번호 + 크기 테이블을 만들어 두는 전처리.

## 코드 리뷰 피드백 (개선점)
- **🔴 진짜 버그 — `roomSize[max_n]`(50칸)**: 방 번호로 인덱싱하는데 방 개수는 최대 `n*m=2500`개(모든 칸이 15면 각자 방). `Rnum>=50`이면 범위 밖 쓰기(UB). → `roomSize[max_n * max_n]`로 잡아야 함. 채점 통과는 운.
  - **교훈**: 방 번호로 인덱싱하는 배열은 "방 최대 개수 = 칸 수"만큼 잡는다.
- 방향 주석 오류: "남동북서" → 실제 `서북동남(1서/2북/4동/8남)`. 코드와 반대라 수정 필요.
- 미사용 변수 `tempRet3` 제거.
- `l` 임시변수 불필요 → `cin >> board[i][j]`.
- (선택) `roomNum`을 `-1` 초기화하면 `visited` 배열 없이 방문 체크 가능.
- (선택) 네이밍: `RoomCnt`/`ret2`/`ret3` → `roomCount`/`maxRoomSize`/`maxMergedSize`로 의미화.
- (선택) `ret3` 루프는 같은 벽을 양쪽에서 2번 검사하지만 `max`라 결과 동일(비효율, 정답엔 무영향).

## 배운 점
- 플러드필 결과에 **번호·크기 메타데이터를 입혀 후처리**하는 패턴.
- 가변 개수 영역(방/그룹)을 인덱싱하는 배열은 **이론상 최대 개수(=원소 수)**로 크기를 잡아야 한다.
